How to extend this system

Written for whoever builds the next tool. Three rules and a check.

Adding a token

  • First ask whether you need one. Nine times out of ten the value exists - a tint is --surface-2, a quiet label is --ink-3, a status is a --bar-* plus a --st-* pair. Steps 5, 6 and 7 added nine tokens between them across eleven page archetypes; that ratio is the target.
  • Name it for its job, never its value. --diff-add-bg, not --green-50. A future re-skin changes hex; it should not change class names or component code.
  • Add it in both themes, in the same group, in the same order. Every token is declared twice: once under :root and once in the dark block. A token that exists in one theme only is a bug that ships silently in the other.
  • Check the contrast before you commit it. Body text and icons that carry meaning need 4.5:1 against the surface they sit on; borders and large text need 3:1. If a brand colour cannot make it - the mustard and coral in the BC guide do not, on white - keep it as a fill and derive a darker *-text sibling, which is exactly why the semantic set is a triple of fill / -bg / -text.
  • Legacy names stay resolvable through the aliases at the bottom of tokens.css. Add to that block rather than renaming in place when a name has to change.

Adding a component variant

  • Prefer a modifier over a new block. .btn--danger is a modifier; a "delete button" is not a component. If your new thing shares the block's box and differs in colour, size or emphasis, it is .block--modifier.
  • State goes in .is-*, not in a modifier. .is-selected, .is-open, .is-loading, .is-dragging are runtime; --primary, --sm are authored. Blazor toggles the former and never the latter, which is what keeps the hand-translation cheap.
  • A variant is not done until all eight states exist: default, hover, focus-visible, active, disabled, loading, error, empty. This is the whole reason the system exists - drift starts in the states nobody drew.
  • Never restate a status colour. Status language is one triple everywhere: a 3px --bar-* keyline, a --st-* or semantic pill, and a word. Any two of those may be dropped for space; the word may not.
  • Reference tokens only. A raw hex in a component file is a defect, not a shortcut - grep for # in the component layers before a PR.

Adding a page that stays cohesive

  • Start from an archetype, not from a blank file. Fourteen exist. A CRUD screen is 3 or 6; a wizard is 13; a data tool is 9, 10 or 11; a read-only reference is 12. If your page is genuinely none of them, that is worth a conversation before it is worth CSS.
  • Put layout in a page layer, not in the component layer. pages-forms.css, pages-power.css and pages-content.css hold grids, sticky offsets and page-specific composition; components.css holds things that appear on more than one page. Do not reach back into a component to make one page work.
  • Pick the density deliberately. Balanced is the default. Reach for .u-compact only for a grid, a source view or a diff - and apply it on the page root so the shell around it is unaffected.
  • Every page gets one primary action, one sticky header, one scroll container. Power tools scroll their panes; everything else scrolls the content column. Two scrollbars in one column means the layout is wrong.
  • Copy is part of the system. CRONUS for sample data, ASCII punctuation, sentence case, no exclamation marks. Errors say what happened, whose fault it is, and what to do next.

The check before you ship

  • Open this sheet in both themes and put your new surface beside its neighbours. Cohesion is a comparison, not an opinion.
  • Tab through the whole page. Every interactive element shows the one focus ring; nothing is reachable without a visible state.
  • Set the density switch the other way. Nothing may overlap or clip.
  • Zoom the browser to 200%. Measures in ch and heights in tokens survive it; hard pixel widths do not.
  • Grep the diff for #, px outside the token file, and any !important. Each one is a question to answer, not necessarily a fault.
