Deployment pipeline

One deployment pipeline, read by someone who was just told "the deployment to Contoso's test environment failed". The summary card answers "is this healthy"; the deployments list answers what, when, how long and why without leaving the page. Built on the detail archetype (PageDetail); like PageEnvironmentDetail, data stored by AL Workbench and data read live from Business Central sit in separate, labelled blocks. Desktop frames are 1440px shells scaled down; phone frames are 390px at 1:1.

Spec

Head

  • Title is the pipeline name; the pill is the environment type: status-pill--danger for Production, --muted for Sandbox. Actions: "All deployments", "Edit", and the one .btn--primary "Release".
  • Same-name safety: source and environment are never printed bare. The sub line reads build pipeline "Test" into the Sandbox environment "Test"; the summary labels each ("Source ... build pipeline", "Environment ... Sandbox"). A pipeline called "Deployments Test into Test" still reads unambiguously.

Summary card

  • Top keyline and heading take the health colour: Healthy (success), Last deployment failed (danger), Scheduled (queued). The sentence says what the environment runs now, which is the question after "it failed".
  • Left block, "This pipeline": stored by AL Workbench - source, when installs run, schema sync, last and next deployment. Right block, sunken, "From Business Central, 4 min ago": environment, type, health, version, next update. The delivery window is stored on the environment by whoever set it up, so it sits on the left. Never mixed.
  • Force sync carries the warning triangle; on a Production pipeline it also gets a alert--warn saying the data is deleted.

Deployments list

  • Collapsed row, 50px: chevron / state glyph / Deployment n + build / outcome word + relative time / started / took / apps / row actions. Same glyph + right keyline vocabulary as every table. States: scheduled, claimed, uploading, installing (spinning arc), deployed, failed, cancelled, handed to Business Central.
  • Row actions only where they mean something: failed gets "Deploy again", scheduled gets "Reschedule" and "Cancel". No kebab.
  • Expanded: failure sentence (alert--danger) that names the app, the cause and what the environment still runs; a step strip with times and durations; per-app results (pending, uploading, installing, scheduled, completed, failed, skipped) with version change and an optional message; a diagnostics log, open by default only on failures, error lines in --danger-bg. The log is the one place mono is used.
  • Drawn from data not recorded yet (issue #929): per-app timings, the version an app moved from, the "Uploaded" step, who cancelled. Until it lands the port hides those cells rather than inventing a value. "Deployment 49" is a per-pipeline sequence computed for display.
  • "Waiting for approval" (future) sits above the newest deployment in --warning-bg with Approve / Dismiss as secondary buttons, so it never competes with "Release".
