AL Dev Toolbox - design system - step 4

Standard page archetypes

Seven layouts that between them cover most of the toolbox, each shown inside the real shell: the tool launcher, the list/browser workhorse (all three states, both table and card views), the cross-solution Environments list, the actionable list with its command bar, master-detail, environment detail, and the calm admin dashboard. The four original frames switch between light, dark or both. Every frame is a real 1440px desktop shell, scaled down with a fixed CSS transform so the shell's own container queries still see a desktop - scroll inside one to see the sticky page header and the live interactions.

Spec

Files

  • pages.css - archetype layout layer. Depends on tokens.css + components.css; layout only, no new colour or type values.

Shared scaffolding

  • .page - the vertical rhythm every archetype sits in (grid, --space-5 gap). .page__hero / __hero-title / __hero-sub for the launcher's larger greeting; ordinary pages use .page-head from step 2.
  • .state-label - the small rule-and-caption marker used on this sheet to separate loading / empty / populated. Not shipped in the app.

15. Actionable list (command bar)

  • .cmdbar (components.css) + __row / __group / __search / __note. Structure taken from the Business Central ribbon - a persistent command bar above the table, commands grouped and separated, the rest behind one overflow - and nothing else: it is drawn entirely in our own tokens and composes .btn, .ra / .menu, .search and .select-wrap rather than owning a button of its own.
  • One filter control, not a select plus a loose checkbox: the "only with an update waiting" flag is a named view inside the same .select, with the combinations spelled out. Two controls for one job made the row ragged and left the checkbox floating between the select and the search.
  • .cell-stack + __main / __sub - a two-line cell for a value and its qualifier: environment over its type, next version over its date. Inline, the second part starts at a different x on every row and the column cannot be scanned; stacked, both lines have a fixed left edge and the row reads as one fact with a footnote.
  • .ra--up flips a row menu above its button. Rows near the foot of a scrolling list have no room below them and the content column clips what escapes; the page's open handler measures the button against the scroll container and sets the class.
  • One row, in the order the work happens: filter, then search, then commands - so the search and filters that used to straggle across their own ragged row sit on the same grid and the same baseline as the actions. The bar is position: sticky - a bulk action has to still be reachable after you have scrolled to the last row you wanted.
  • The command bar is the page's sticky header, so its page head is a plain .page-head: one sticky element per scroll container, as everywhere else. A page that genuinely needs both pins the head as usual and sets --sticky-head on the page root - .cmdbar reads top: var(--sticky-head, 0px), the same escape hatch .detail-body uses.
  • Selection-dependent commands are plainly disabled until rows are ticked, which is what a BC user already expects from a ribbon. No selection counter and no "tick rows first" instruction: the checkbox column and the disabled buttons say it between them, and a counter that appears and disappears changes the bar's height for no gain.
  • Captions are two words - Move dates, Update now, Refresh - with the full sentence in the title. A command bar is scanned, not read; the long form ("Move dates to the latest") belongs in the tooltip and in the row menu, where there is room for it.
  • The overflow is a single .btn--icon ellipsis holding the rest, including the selection-only commands as .menu__item[disabled]. The timezone caption that used to float above the table is now one clause of the page subtitle, where a fact about the whole page belongs.
  • Row selection is .data-table__col-check + .check, with .is-indeterminate on the header box for a partial selection and tr.is-selected on the picked rows - so the selection is legible in the table, not only in the bar.
  • Per-row commands live in the row's own .ra menu (Update history first). A button repeated down every row competes with the bar for the same job; a menu is the quieter affordance and holds the single-row versions of the bulk commands too.
  • No Status column: the row already carries its state twice, as the leading glyph and the edge keyline, and the glyph's aria-label / title carry the word. That is the rule the sheet states below - tables get the edge bar and glyph, pills belong to cards, detail headers and inline contexts - so a third copy in a column of its own was the table contradicting the system. Version numbers are plain sans with .u-num tabular figures rather than the mono face. The boundary: a short release number you say out loud - 28.2, 28.4 - is sans in every table; a full build identifier you copy and paste - 28.5.0.363410, 1.4.0.882 - stays mono, on the environment detail page where those live.
  • Reusable anywhere a list has bulk actions - Releases, Users, Translator's unit list. The archetype is the bar plus a selectable .data-table--edge; only the columns and the command set change.

Freshness (data read from Business Central)

  • .freshness (components.css) + __icon __text __age __sep __note __spacer, with --stale and .is-refreshing. Exactly one per page, directly under the page head, holding the only Refresh - the old environment panel repeated "checked 10 hours ago" and a Refresh button per section, and neither told you which section the age belonged to.
  • --stale is the same strip escalated to --warning, not a second component, so the copy under it never changes. .is-refreshing mutes the age and pairs with .btn--loading on the action.
  • Row-level ages stay in the table's own "Last checked" column: solutions are polled on their own schedules, so a single page-level age would be a lie for some rows. The strip says so in __note.

2 - variant. Environments list

  • Plain archetype 2: .page-head--sticky, .filter-bar, .data-table--edge, .pager. Columns are customer, environment, now on, next update, last checked - the same set and the same .cell-stack treatment as Upgrades, because the two pages list the same thing. Customer links to the solution, environment to this detail page; Upgrades adds only what scheduling needs on top: a selection column and the latest possible date.
  • Status is the row's edge keyline plus its leading glyph - tr.is-published / .is-running / .is-failed / .is-queued, with the word on the glyph's aria-label and title. No Status column: a pill there would be the third copy of the same fact, and pills belong to cards, detail headers and inline contexts. Unreachable and Suspended are real states here, not blanks.
  • The empty state is written for a first run: environments appear once a solution has a Business Central connection, so the primary action is Connect a solution, not New environment - the toolbox cannot create one.

3 - variant. Environment detail

  • Header band is the standard .detail-head + .page-head__crumbs back to the solution, with status pill and type .tag beside the name, and "Open in Business Central" as the one outbound action. .meta-row carries version, country, windows and app count.
  • Then three .card blocks, in the order a consultant reads them: Updates (.kv-grid of current version, next version, date, latest possible date, our delivery window beside BC's own window, plus an .alert--info when the two overlap), Apps, and Environment settings.
  • Apps is three separately headed cards, never one column: scheduled installs (.empty-state--quiet plus the "do not use both places" caveat), installed apps (plain .data-table, capped with a Show all footer), and AppSource updates waiting.
  • The waiting list was ~25 ragged text lines with inline "needs X, Y first" notes. It is now .data-table--edge.u-compact with App / Publisher / Target version / Prerequisites, its own filter and search, and a state column that turns the dependency note into a sortable status - Ready against tr.is-published, Waits for N against tr.is-queued - with the blocking apps as .tag chips. Ready rows sort first, so the work you can actually do is at the top.
  • Settings use .setting-list with an .alert--warn above them and .setting--danger + .setting__lock on the one that reschedules the tenant's update: the existing "this writes to the customer's tenant" treatment, unchanged.

1. Tool launcher

  • .tool-grid - auto-fill, minmax(232px, 1fr), so it reflows from 4 columns to 1 without breakpoints.
  • .tool-tile (an <a>: the whole tile is the hit target) + __icon / __title / __text / __meta. Hover flips the icon chip to a solid --primary-strong and the title to teal; focus uses the standard ring.
  • .tool-tile--locked - dashed border, muted ink, cursor: not-allowed, plus a .tool-tile__lock pill. Rendered as a <span role="link" aria-disabled>, never an <a>, so it cannot be followed. Copy says what unlocks it.
  • Tiles are grouped under .section-label headings (Build / Translate and compare / Deliver) rather than one flat wall.

2. List / browser

  • .filter-bar + __search / __spacer; .view-switch / __btn + .is-active toggles table vs cards per tool.
  • Table view reuses .data-table unchanged. Card view adds .card-grid and .browse-card + __top / __title / __text / __tags / __foot.
  • Table view carries status as the 4px right edge bar plus a leading icon-only state cell (.data-table--edge + tr.is-published / .is-draft / .is-archived), so a scanned list reads as one spine of colour and no column is spent on a word. Card view keeps the .status-pill - a card has no shared edge to line up. Both carry a per-row/card kebab (.ra + .menu).
  • Three states, all rendered: loading (skeleton cells under the real header, so column widths don't jump, plus a .loading-block caption), empty first-run (.empty-state + one .btn--primary), populated. A fourth is included that teams always forget - filtered-empty, which offers "Clear filters" instead of "New", because "no templates yet" is a lie when 18 exist.

3. Master-detail

  • .detail-head + __title-row / __title - title, status pill, primary split action, kebab.
  • .meta-row / .meta-item + __label / __value (--mono for branches and refs) - a responsive key/value strip, auto-fit minmax(148px).
  • .pill-tabs switch sub-views (Runs / Steps / Variables / Artifacts / Permissions).
  • Run history is a real .data-table with sortable columns - Run, Description, Trigger, Commit, Branch, Started, Duration - not a bespoke row layout, so it sorts, filters and scans like every other table in the toolbox. .commit-chip is the short git ref with a git-commit glyph.
  • Status is a 4px right edge bar plus a leading glyph, no label column: .data-table--edge with tr.is-succeeded / .is-failed / .is-running / .is-queued / .is-cancelled. The first cell is .data-table__col-state holding an icon-only .data-table__state--icon (.data-table__state--spin animates the running loader). Dropping the word saves a column and the eye still gets three signals: bar colour, glyph shape, and the accessible name in aria-label + title - so it never depends on colour alone.
  • The bars have their OWN token set rather than reusing the pill fills, because a 4px mark must clear 3:1 against --surface and --info / --border-strong measure only 2.2:1 and 1.6:1 - a queued row would have read as no bar at all. --bar-succeeded, --bar-failed, --bar-running, --bar-queued, --bar-cancelled, --bar-published, --bar-draft, --bar-archived, all >=3:1 in both themes; .run-row--* in pages.css uses the same tokens.
  • The failed row is selected to demonstrate .is-selected plus its open kebab; a second table below shows the selected run's steps with the same treatment. .run-list / .run-row stay in pages.css for card-like histories that are not tabular.

4. Dashboard (Admin)

  • .cue-grid is a fixed 6 / 3 / 2 column grid rather than auto-fit, so a row never strands one tile beside empties - and the count comes from a @container query on the grid's own width, not the viewport, because these tiles sit inside scaled frames and half-width panels. It now lives in components.css: a cue is a component, and both dashboards compose it. .cue + __label / __value / __rule / __foot / __drill - BC activity-indicator cues: solid fill, large plain number, a rule under it, and a drill-down chevron. The whole tile is the link.
  • Attention is expressed by the FILL, not a badge: .cue--attention turns the tile red (--cue-attn-bg) and thickens the rule, the way BC cues do. No warning pill needed - the colour of the tile is the signal, so a screenful of cues reads at a glance.
  • Cue tokens: --cue-bg, --cue-bg-hover, --cue-ink, --cue-ink-dim, --cue-rule, --cue-attn-bg, --cue-attn-bg-hover. Light uses a darkened BC teal-slate #3F6C72 and cue red #A0403C so white labels clear 4.5:1 and the 11px foot line clears it too at --cue-ink-dim #EAF3F4; dark deepens both.
  • Every cue carries a "last activity" line in __foot, so a count always says how fresh it is.
  • .dash-grid / .dash-tile remains available as the quieter outlined variant for sections where a wall of filled colour would be too loud.
  • .dash-cols - two equal columns collapsing at 900px - holds .activity / .activity__row + __avatar / __icon / __body / __text / __sub / __time.
  • The "Needs attention" list uses .activity--edge with row states .is-warning / .is-failed / .is-queued / .is-open / .is-succeeded - the same 4px status spine as the tables, on the same --bar-* tokens. Its pills are gone; the leading icon chip is tinted to match and the time column goes back to being a time. Recent activity stays unstatused - those rows are history, not work items.
  • Deliberately calm: no charts, no gauges, muted timestamps, and red used only where a human must act. It is a landing page - the numbers are entry points, not telemetry.

Status placement, one rule

  • One pattern for every table: .data-table--edge + a row state class (run states tr.is-succeeded / .is-failed / .is-running / .is-queued / .is-cancelled, lifecycle states tr.is-published / .is-draft / .is-archived) and a leading .data-table__col-state cell. Rule: table and list rows get the edge bar and glyph; cards, detail headers and inline contexts keep .status-pill. .u-sr hides the state column's header text from sight but not from screen readers.

Shell integration and performance

  • ShellFrame gained a body prop (pipelines | launcher | list | detail | env-list | env-detail | upgrades | dashboard | ...) so archetypes mount inside the real shell rather than a mock-up of it, plus bodyKind (populated | loading | empty, for the list states) and upgradesSelected (seeds the actionable list’s selection). The shell also derives its own active nav item from body, so a frame showing Environments highlights Solutions > Environments rather than whatever was hard-coded.
  • Frames scale with a fixed per-breakpoint transform: scale() - no measurement, no observers, no JS. Two optimisations were tried and removed: content-visibility: auto, whose auto intrinsic size is derived from the element's own last render and so oscillates between skipped and rendered, relayouting repeatedly; and observer-gated animation-play-state, which froze the very loading states this sheet exists to demonstrate. Each archetype mounts ONE frame with a light / dark / both switch, and the inactive pane is not rendered at all (sc-if, not display: none) - so only the shell you are looking at is ever constructed. This is spec-sheet scaffolding, not app code - the Blazor app renders one shell, unscaled.

Tokens added

  • Seven cue tokens (--cue-*) for the BC activity-indicator tiles, and eight --bar-* status-indicator tokens, all in both themes. Everything else resolves from steps 1-3; the only new animation is al-indeterminate for the running-build bar, coloured with --info.

Which archetype per tool

  • Launcher Home. List Templates, Cookbook, Solutions, Pipelines, Releases, Admin Users. Actionable list Upgrades, and any list with bulk actions. Detail solution / pipeline / release / release-run pages, and Environment detail. Dashboard Admin and Site-admin landings. Object Explorer, Translator, Diff and Piper are the data-heavy power tools - they need their own archetype and are not covered here.
